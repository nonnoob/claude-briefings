# 输出产品前把会话分支也推平

> 补充 ADR-0005：该 ADR 规定落盘只推 `claude/<topic-slug>-<YYYY-MM-DD>` 一个分支，自本决策起在其后追加一次对会话自身分支的推送。

落盘的推送步骤变成两次：先照 ADR-0005 推任务分支，再在当前分支不是 `main` 时执行 `git push -u origin HEAD`，把同一个提交推到与会话分支同名的远端分支，并用 `git status` 确认工作区干净。两次推送都完成之后才输出产品。

决策依据：云端会话检出在平台生成的分支 `claude/<形容词>-<人名>-<哈希>` 上，平台带一个结束钩子——会话结束时若该分支有未推送的提交或未提交的改动，钩子会把模型重新唤起去补推。ADR-0005 只推任务分支，会话分支在钩子眼里始终"有未推送的提交"，于是每次运行都是：输出简报 → 钩子唤起 → 推会话分支 → 为了满足"产品是最后一条消息"再输出一遍简报。2026-10-01 在 `ai-industry-briefing` 的运行记录里直接看到这个序列（两份简报之间夹着 `Hook re-prompted Claude` 与 `Pushed claude/affectionate-tesla-tjrzxw`），Actions 历史也吻合：每个任务分支推送后 30–70 秒必有一次会话分支推送，天天如此。

此前（2026-08-14）把它当成模型的顺序问题，在正文里补了"只输出一次"。那条规则挡不住：模型输出简报时所有该做的动作确实都做完了，钩子是在它之后才出现的。此前还把会话分支的推送记成"平台自动推送"，同样是误判——那是钩子唤起后模型自己推的。

## Consequences

- 每次运行会触发两次 auto-merge Action。第二次相对 main 无改动，Action 只删除分支，不产生提交；这与改造前的实际情况相同，只是顺序提前到了产品之前。
- 不改成"只推会话分支"：任务分支名确定可读（ADR-0005 的理由仍成立），而会话分支在本机手动运行时可能就是 `main`，不能作为唯一推送目标。
- 产品定义加一个例外：钩子仍然唤起时（原因不限于推送），只做它要求的动作并以一行指针结束，不重贴简报。此时会话的最后一条消息不是简报——重复输出比这更糟，这是有意的取舍。
- 验证方法：打开任一 Routine 的运行记录，简报只出现一次、其后没有 `Hook re-prompted Claude`。
