- 覆盖窗口 = 自上次运行时刻至现在，封顶 7 天。两种边界：

## 第 2 步：检索

- **按当前当地时间定侧重**：正午之前运行，"今明速览"侧重当天下午到晚上；傍晚运行，侧重当晚和第二天；周四、周五运行时把整个周末都算进来。

检索要求：

- 每个方向至少用 2 组不同的检索词，一组搜橙县、一组搜洛杉矶；"美食饮品"和"全国范围"不得因为第一次没搜到就放弃，换检索词再搜。
- 每个准备收录的活动，再用"活动名 + 场馆"做一次定向检索，核实日期、时间、地点和票价。
- 核实不到日期或地点的不收。只核实不到票价时如实写"票价未公布"；**不要写"请查官网"**——读者要的是信息，不是去哪查的指路。
- 来源用主办方或场馆官网，或上面列出的本地媒体。房产中介博客、SEO 聚合站一类的页面只能当线索，不能当来源。
- 云端环境的 WebFetch 常被网络策略拦截（EGRESS_BLOCKED）。被拦一次就不要再试，改用定向 WebSearch 取细节。

明确排除：

- 时事新闻（政治、经济、社会）由时事简报覆盖，本简报不收。
- 没有具体日期和地点的常青推荐清单（"洛杉矶必吃 20 家"一类）、纯广告与普通打折促销。
- 行业会议、商业展会、会员制或邀请制的私人活动；面向公众的大型展会（车展、动漫展等）照常收。
- 已经结束的活动；已售罄且没有加场的活动。

通用规则：

- 日期、时间、地点、票价以主办方或场馆官方页面为准；媒体转述与官方页面不一致时以官方为准，并尽量把来源挂到官方页面。日期无法确认的活动不收。
- 去重按**事件级语义**判定：与已报条目描述的是同一事件的（换了媒体、标题、链接也算），跳过。同一活动的不同场次算同一事件。
- 已报事件出现**实质性新进展**的，作为续报收录：条目前加【续报】，只写增量，不重复旧细节。本任务的实质性新进展包括：加场、改期、取消、售罄、票价变化。
- 提醒也算续报，但要克制：已报活动走到关键节点时（今天开票、今天或今晚开始、最后一个周末）可以再提一次，条目前加【续报】，只写提醒点。每个活动每类节点至多提醒一次。
- 逐一检查进行中事件表：按各事件"下一步关注点"给出的具体预期定向检索验证（不止泛搜"有无新消息"），有新进展则续报并更新其关注点，无则保留待下次。本任务的进行中事件主要是"已报、但关键节点还没到"的活动，关注点写成带日期的节点（如"10 月 10 日上午 10 点开票""11 月 2 日闭展"）。
- 优先可信一手来源；重大、争议或反直觉的信息尽量用第二独立来源交叉验证。重要条目只有单一信源、交叉验证未果仍收录的，条目前加【单源】；多个可信来源说法矛盾的，条目前加【矛盾】并列出两说及各自来源，不擅自裁决。
- **可信度门槛是"有可信来源"，不是"已被多源证实"**：交叉验证只决定加不加标记，不决定收不收。只找到聚合站、转载或社交平台来源、一时找不到一手原文的，照常收录，加 【单源】，并在条目里写明消息出自哪里；只有明显是旧闻、已被辟谣或来源完全不可信时才舍弃。
- 发布时间难以精确确认、但不在已报条目中、内容看起来是新动态的，照常收录，在条目正文末尾（`来源：` 之前）注明 （发布时间未确认）；不要因为日期核实不了、网页打不开（WebFetch 被拦）就舍弃，改用 WebSearch 摘要作依据。
- 判定空期前必须补搜一轮：换关键词（中英文互换、具体公司/产品/人名、加"今天""本周"等时间词）、换来源（官方新闻室、新闻聚合页、社交平台热榜）再搜一遍。只有补搜后仍找不到任何未报过的新动态，才用空期骨架。
- 传闻显式纳入采集范围：有可信度的爆料源（有 track record 的爆料人、行业内部人士、供应链/渠道消息）照常收录，不因"未官宣"而跳过——官方消息往往滞后。传闻条目前加【传闻】，条目内写明消息出自谁；不得把传闻表述为既成事实。传闻默认登记进"进行中事件表"追踪，待证实或辟谣时以续报闭合。本任务的传闻主要是未官宣的巡演站点、开店计划与联名活动。
- 单个方向失败时降级，不中止整轮：某个检索方向被平台安全策略拦截（safeguards flagged / request blocked）、工具报错或检索配额耗尽时，跳过该方向、继续执行其余方向，按"部分成功"落盘，并在运行备注与 MEMORY.md 中注明该方向本期未覆盖。只有全部方向都无法取得任何有效内容，才算"完全失败"。

## 第 3 步：格式契约

简报的结构由下面这份骨架**逐字**规定。骨架里的 `#`、`##`、`- `、`> ` 是字面格式，不是排版强调；`<>` 里的才是要替换的内容。

```
# 🎡 南加吃喝玩乐 · <YYYY-MM-DD>

> 覆盖窗口：<起> 至 <止>（常规 / 补漏：<原因>）

今日要闻：<一句话，本期最重要的一条>

## <板块名>

- <一句话：什么活动 + 何时 + 在哪 + 亮点 + 价格或是否需预约>。来源：<来源名称> <URL>
- 【续报】<只写增量，不重复旧细节>。来源：<来源名称> <URL>

## <板块名>

- 【传闻】<消息出自谁>：<内容>。来源：<来源名称> <URL>
```

全部板块都无实质新内容时（少见），用空期骨架，**不得编造内容凑数**：

```
# 🎡 南加吃喝玩乐 · <YYYY-MM-DD>

> 覆盖窗口：<起> 至 <止>（常规）

本期没有值得报告的内容：<一句话说明各方向均已检索、展望期内无未报道过的活动>。
```

板块与顺序：今明速览、美食饮品、演出与赛事、展览艺术、节庆市集与玩乐、全国范围（按此顺序，只出现当期有内容的板块）

必须满足、且会被仓库内看门狗机械校验的几条：

- 一级标题恰好一行，以 `# ` 开头，位于全文最前。
- 覆盖窗口行紧随标题，以 `> ` 开头，**每期都有**，无论窗口是否常规。
- 板块一律用 `## `。**不得**用粗体、下划线或任何其他写法代替板块标题。
- 条目一律用 `- ` 开头的单行。条目**不得**以 `**` 开头。
- 每条必须以 `来源：<来源名称> <URL>` 结尾。URL 用裸链接，**不用** `[名称](URL)` 这种 markdown 链接语法——裸链接能让读者一眼看见域名，配合【单源】判断可信度。
- 确实拿不到公开链接的（页面已下架、仅有转引等），写成 `来源：<来源名称>（无公开链接：<原因>）`。**缺链接必须显式化**——否则"本来就没有"和"忘了挂"从产出上无法区分。
- 标记只作为条目最前缀出现，可叠加，顺序为【续报】【传闻】【单源】【矛盾】中实际适用者。
- 没有实质新内容的板块整节省略，不保留空标题。
- 有条目的简报，覆盖窗口行之后紧跟一行 `今日要闻：`，用一句话点出本期最重要的一条（从下方条目中选，不另挂来源；分量相当时选对读者影响最直接的）；空期骨架不写此行。

内容要求：每节至多 2–4 条，"全国范围"至多 2 条，优先信号最强的内容；每条一句话讲清楚，可快速扫读，不注水。
- 每条写清四件事：什么活动、何时（日期带星期，有钟点就写钟点）、在哪（场馆与城市）、多少钱或是否免费、是否需要预约或抢票。
- "今明速览"只放今天和明天就能去的活动，不限类别；一个活动只出现在一个板块，放进"今明速览"的就不再放进后面的板块。
- 同等条件下橙县的活动排在洛杉矶的前面。
- 每节至多 1 条"远期预告"（7 天以后的活动），并且只收需要现在就行动的（正在开票、即将售罄、需要预约）。

## 第 4 步：落盘（成功才落盘；顺序固定：先归档、后记忆、再推送、最后回复）

- **完全失败**（检索全挂、未取得任何有效内容）：不写归档、不改 MEMORY.md，直接说明失败原因即结束——下次运行的窗口会自动覆盖这段时间。
- **部分成功**（个别方向检索失败）：照常落盘，在 MEMORY.md 与运行备注中注明哪些方向本期未覆盖。
- 先写归档：`archive/local-events-briefing_<YYYY-MM-DD>.md`（运行当天实际日期）；当天已存在同名文件时改用 `local-events-briefing_<YYYY-MM-DD>_<HHmm>.md`——**永不覆盖已有归档**。归档内容 = 第 3 步骨架产出的简报正文，到最后一个条目为止；**运行备注不写进归档**（它描述运行状态，不是内容）。
- 落盘前自检一遍：对照第 3 步那几条硬规则逐条核对本期产出，不合格就改完再写文件。
- 后整体重写 `MEMORY.md`，固定三节：
  1. 本次运行时刻与实际覆盖窗口；
  2. 已报条目清单：保留最近 21 天，一行一条，格式"日期 | 一句话事件描述（什么活动 + 活动日期 + 地点）| 代表性链接"，描述只写事件本身、不携带"(同日二次运行)"之类的运行批注；
  3. 进行中事件表：预期还有后续、需要跨运行追踪的事件，每条含"事件、最后进展日期、下一步关注点"，关注点写成具体可验证的预期（如"等 X 官宣""10 月 10 日开票"），供下次定向检索；事件已闭合（活动结束、关注点日期已过）或连续 28 天无新进展则移出；至多保留 15 条，按重要性取舍——因条数上限而踢出仍在推进的事件时，在运行备注注明踢出了哪条、为什么。
- 再提交推送：`git add` 本任务根目录并 commit（消息格式 `local-events-briefing: <YYYY-MM-DD>`）。**推送目标固定为分支，不要尝试直推 main**：`git push origin HEAD:refs/heads/claude/local-events-briefing-<YYYY-MM-DD>`；若该分支已存在导致推送被拒，改用 `claude/local-events-briefing-<YYYY-MM-DD>-<HHmm>` 重推一次。仓库内的 auto-merge 工作流会把它并入 main 并删除分支。**推送走哪个分支名不是异常，不要写进运行备注。**仅当推送彻底失败（两次都被拒）时才在运行备注告警。
- 推完任务分支后，把会话自己的分支也推平：先看 `git branch --show-current`——输出一个分支名且不是 `main` 时，执行 `git push -u origin HEAD`（把同一个提交推到与当前分支同名的远端分支）；输出为空（游离 HEAD）或就是 `main` 时跳过。然后用 `git status` 确认工作区干净。**这一步不能省**：平台的结束钩子发现会话分支上有未推送的提交或未提交的改动时，会在你输出简报之后把你重新唤起去补推，简报就会被输出第二遍。这次推送的成败同样不写运行备注。
- 归档永久保留：不删除、不清理 `archive/` 下任何文件（非交互运行中删除文件会触发权限请求而中断任务；清理只由用户手动进行）。

## 运行结束：产品

本次运行面向用户的交付物，是**会话的最后一条消息**。它的正文必须是刚写入归档文件的那份简报，**逐字相同，不得增删、不得改写**。

- **不得**用"已完成""详见仓库""见 archive"之类的指针或摘要代替简报正文。
- 最后一条消息里只允许两样东西：简报正文；以及仅在本次运行确有异常或特殊动作时（MEMORY.md 缺失重建、部分方向未覆盖、补漏封顶截断、事件表因上限踢出、推送彻底失败），末尾追加的一行普通文字 `运行备注：<一句话>`。不用尖括号标签，不重复简报内容。
- **它必须是本次会话的最后一条消息，且只输出一次**：写文件、改记忆、commit、push 全部在它之前完成；输出它之后，不得再发起任何工具调用、不得再补任何说明。若发现还有动作没做完，先把动作做完再输出简报，而不是输出一次、做完动作、再输出一次。唯一例外：输出之后仍被平台的结束钩子重新唤起时（例如要求提交或推送），只做它要求的动作，然后以一行 `简报已在上一条消息完整给出。` 结束——**不要把简报再贴一遍**，也不要解释或汇报。
- **全程不要写旁白**：不要用自然语言描述自己正在做什么（"现在提交并推送……""让我先回滚一下……""Now committing and pushing…"），也不要在工具调用之间做进度播报。工具调用本身就是记录，不需要解说。需要留痕的判断写进 MEMORY.md，不写进对话。
- **通知**：如本会话有通知类工具并选择发送，通知正文只写简报的实质内容（可压缩为要点），**不得出现分支名、推送、归档、合并、工作流等任何运行细节**——通知是给读者看活动的，不是运维回执。
