- 本任务为**周更**：常规覆盖窗口约 7 天。
- 覆盖窗口 = 自上次运行时刻至现在，封顶 10 天。两种边界：
  - 首次运行（无记忆亦无归档）：按过去 7 天处理；
  - 缺口超过封顶（久未开机）：窗口内正常收录，窗口外只收至今仍重要的大事。

## 第 2 步：检索

按以下方向用 WebSearch 检索（可辅以对具体站点的定向搜索）：

- **核心项目版本与变更**：Kubernetes、Istio、Envoy、Helm、Flux CD、Argo（CD/Workflows/Rollouts）、Cilium、containerd、etcd、Prometheus、OpenTelemetry 等主流项目的正式版本发布、重要 alpha/beta 特性、废弃与破坏性变更。优先源：kubernetes.io/blog、各项目 GitHub Releases、LWKD（Last Week in Kubernetes Development）、KubeWeekly。
- **安全与漏洞**：上述项目及容器运行时、镜像供应链（如 runc、BuildKit、镜像仓库、Sigstore 生态）的 CVE、安全公告、在野利用报告。优先源：GitHub Security Advisories、各项目安全邮件列表公告、Wiz/Sysdig/Aqua 等云安全厂商研究博客。
- **云厂商托管服务**：AWS（EKS 为主）、Google Cloud（GKE）、Azure（AKS）的新功能、版本支持矩阵变化、定价调整、区域可用性；其他影响云原生工作负载的重大云厂商动态。优先源：AWS What's New / Containers Blog、Google Cloud Blog、Azure Updates。
- **CNCF 与社区生态**：CNCF 项目毕业/孵化/归档、TOC 决策、KubeCon 等大会的重要发布与议题、有影响力的开源治理事件（如 license 变更、项目分叉）。优先源：cncf.io/blog、CNCF 公告、The New Stack、InfoQ。
- **商业与产业动向**：云原生领域厂商的融资、并购、产品线调整（如 Red Hat/OpenShift、SUSE/Rancher、HashiCorp、Isovalent、Solo.io 等）；影响 GitOps/平台工程方向的商业事件。
- **工程实践与技术趋势**：高信号的架构实践文章、大规模生产事故复盘（postmortem）、平台工程/GitOps/eBPF/WebAssembly 等方向的重要技术进展。优先源：知名公司工程博客、Hacker News 高热度讨论。

排除项：

- 与云原生无关的泛云计算/SaaS 应用新闻（如办公协作软件更新）；
- 纯营销软文、无实质内容的厂商 PR 稿；
- 与容器/编排生态无关的通用 AI 模型新闻（AI 基础设施与 K8s 结合的内容照常收录）。

通用规则：

- 只收录发布时间落在覆盖窗口内的内容。
- 去重按**事件级语义**判定：与已报条目描述的是同一事件的（换了媒体、标题、链接也算），跳过。
- 已报事件出现**实质性新进展**的，作为续报收录：条目前加【续报】，只写增量，不重复旧细节。
- 逐一检查进行中事件表：按各事件"下一步关注点"给出的具体预期定向检索验证（不止泛搜"有无新消息"），有新进展则续报并更新其关注点，无则保留待下次。
- 优先可信一手来源；重大、争议或反直觉的信息尽量用第二独立来源交叉验证。重要条目只有单一信源、交叉验证未果仍收录的，条目前加【单源】；多个可信来源说法矛盾的，条目前加【矛盾】并列出两说及各自来源，不擅自裁决。
- 传闻显式纳入采集范围：有可信度的爆料源（有 track record 的爆料人、行业内部人士、供应链/渠道消息）照常收录，不因"未官宣"而跳过——官方消息往往滞后。传闻条目前加【传闻】，条目内写明消息出自谁；不得把传闻表述为既成事实。传闻默认登记进"进行中事件表"追踪，待证实或辟谣时以续报闭合。
- 单个方向失败时降级，不中止整轮：某个检索方向被平台安全策略拦截（safeguards flagged / request blocked）、工具报错或检索配额耗尽时，跳过该方向、继续执行其余方向，按"部分成功"落盘，并在运行备注与 MEMORY.md 中注明该方向本期未覆盖。只有全部方向都无法取得任何有效内容，才算"完全失败"。

## 第 3 步：格式契约

简报的结构由下面这份骨架**逐字**规定。骨架里的 `#`、`##`、`- `、`> ` 是字面格式，不是排版强调；`<>` 里的才是要替换的内容。

```
# ☁️ 云原生周报 · <YYYY-MM-DD>

> 覆盖窗口：<起> 至 <止>（常规 / 补漏：<原因>）

## <板块名>

- <一句话：谁 + 做了什么 + 关键数字或影响>。来源：<来源名称> <URL>
- 【续报】<只写增量，不重复旧细节>。来源：<来源名称> <URL>

## <板块名>

- 【传闻】<消息出自谁>：<内容>。来源：<来源名称> <URL>
```

全部板块都无实质新内容时（少见），用空期骨架，**不得编造内容凑数**：

```
# ☁️ 云原生周报 · <YYYY-MM-DD>

> 覆盖窗口：<起> 至 <止>（常规）

本期没有值得报告的内容：<一句话说明各方向均已检索、窗口内无未报道过的实质新内容>。
```

板块与顺序：版本与变更、安全通告、云厂商动态、CNCF 与社区、商业动向、工程实践（按此顺序，只出现当期有内容的板块）

必须满足、且会被仓库内看门狗机械校验的几条：

- 一级标题恰好一行，以 `# ` 开头，位于全文最前。
- 覆盖窗口行紧随标题，以 `> ` 开头，**每期都有**，无论窗口是否常规。
- 板块一律用 `## `。**不得**用粗体、下划线或任何其他写法代替板块标题。
- 条目一律用 `- ` 开头的单行。条目**不得**以 `**` 开头。
- 每条必须以 `来源：<来源名称> <URL>` 结尾。URL 用裸链接，**不用** `[名称](URL)` 这种 markdown 链接语法——裸链接能让读者一眼看见域名，配合【单源】判断可信度。
- 确实拿不到公开链接的（页面已下架、仅有转引等），写成 `来源：<来源名称>（无公开链接：<原因>）`。**缺链接必须显式化**——否则"本来就没有"和"忘了挂"从产出上无法区分。
- 标记只作为条目最前缀出现，可叠加，顺序为【续报】【传闻】【单源】【矛盾】中实际适用者。
- 没有实质新内容的板块整节省略，不保留空标题。

内容要求：每节至多 6 条，优先信号最强的内容；每条一句话讲清楚，可快速扫读，不注水。
- 涉及版本发布或废弃变更时，点明对使用者的实际影响（是否需要行动、影响哪条升级路径）。
- 安全条目标明 CVE 编号与严重程度（如有 CVSS 分数）。

## 第 4 步：落盘（成功才落盘；顺序固定：先归档、后记忆、再推送、最后回复）

- **完全失败**（检索全挂、未取得任何有效内容）：不写归档、不改 MEMORY.md，直接说明失败原因即结束——下次运行的窗口会自动覆盖这段时间。
- **部分成功**（个别方向检索失败）：照常落盘，在 MEMORY.md 与运行备注中注明哪些方向本期未覆盖。
- 先写归档：`archive/cloud-native-briefing_<YYYY-MM-DD>.md`（运行当天实际日期）；当天已存在同名文件时改用 `cloud-native-briefing_<YYYY-MM-DD>_<HHmm>.md`——**永不覆盖已有归档**。归档内容 = 第 3 步骨架产出的简报正文，到最后一个条目为止；**运行备注不写进归档**（它描述运行状态，不是内容）。
- 落盘前自检一遍：对照第 3 步那几条硬规则逐条核对本期产出，不合格就改完再写文件。
- 后整体重写 `MEMORY.md`，固定三节：
  1. 本次运行时刻与实际覆盖窗口；
  2. 已报条目清单：保留最近 21 天，一行一条，格式"日期 | 一句话事件描述（谁+干了什么）| 代表性链接"，描述只写事件本身、不携带"(同日二次运行)"之类的运行批注；
  3. 进行中事件表：预期还有后续、需要跨运行追踪的事件，每条含"事件、最后进展日期、下一步关注点"，关注点写成具体可验证的预期（如"等 X 官宣""等 Y 回应"），供下次定向检索；事件已闭合或连续 21 天无新进展则移出（可在当期简报注一句）；至多保留 10 条，按重要性取舍——因条数上限而踢出仍在推进的事件时，在运行备注注明踢出了哪条、为什么。
- 再提交推送：`git add` 本任务根目录并 commit（消息格式 `cloud-native-briefing: <YYYY-MM-DD>`）。**推送目标固定为分支，不要尝试直推 main**：`git push origin HEAD:refs/heads/claude/cloud-native-briefing-<YYYY-MM-DD>`；若该分支已存在导致推送被拒，改用 `claude/cloud-native-briefing-<YYYY-MM-DD>-<HHmm>` 重推一次。仓库内的 auto-merge 工作流会把它并入 main 并删除分支。**推送走哪个分支名不是异常，不要写进运行备注。**仅当推送彻底失败（两次都被拒）时才在运行备注告警。
- 归档永久保留：不删除、不清理 `archive/` 下任何文件（非交互运行中删除文件会触发权限请求而中断任务；清理只由用户手动进行）。

## 运行结束：产品

本次运行面向用户的交付物，是**会话的最后一条消息**。它的正文必须是刚写入归档文件的那份简报，**逐字相同，不得增删、不得改写**。

- **不得**用"已完成""详见仓库""见 archive"之类的指针或摘要代替简报正文。
- 最后一条消息里只允许两样东西：简报正文；以及仅在本次运行确有异常或特殊动作时（MEMORY.md 缺失重建、部分方向未覆盖、补漏封顶截断、事件表因上限踢出、推送彻底失败），末尾追加的一行普通文字 `运行备注：<一句话>`。不用尖括号标签，不重复简报内容。
- **它必须是本次会话的最后一条消息，且只输出一次**：写文件、改记忆、commit、push 全部在它之前完成；输出它之后，不得再发起任何工具调用、不得再补任何说明。若发现还有动作没做完，先把动作做完再输出简报，而不是输出一次、做完动作、再输出一次。平台可能在会话结束时自动推送本会话的工作分支——那是平台行为，**不要对此作任何解释、汇报或补充消息**。
- **全程不要写旁白**：不要用自然语言描述自己正在做什么（"现在提交并推送……""让我先回滚一下……""Now committing and pushing…"），也不要在工具调用之间做进度播报。工具调用本身就是记录，不需要解说。需要留痕的判断写进 MEMORY.md，不写进对话。
- **通知**：如本会话有通知类工具并选择发送，通知正文只写简报的实质内容（可压缩为要点），**不得出现分支名、推送、归档、合并、工作流等任何运行细节**——通知是给读者看新闻的，不是运维回执。
